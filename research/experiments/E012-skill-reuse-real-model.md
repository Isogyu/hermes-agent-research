# E012 Skill 再利用の効果を実モデルで測る（2026-11-20〜21）

- **目的**: 中心の主張「成功したやり方を Skill にすると、推論が減り信頼性が上がる」を実測する（H1）。
- **仮説と反証条件**:
  - H1a: Hermes が自分で書いた Skill があると、同じ型の作業の呼び出し回数とトークンが減る。反証: Skill なしと差がない、または増える。
  - H1b（反証側）: 手順をコードに固めた Skill は、前提（社内ルール）が変わると黙って誤答する。反証: ルール変更に気づいて正答する。
- **業務**: 架空の月次売上レポート。CSV 60行、為替換算、状態による除外、丸め、出力形式の社内ルールが `docs/reporting-rules.md` にあり、古い矛盾した文書も混ぜてある（`lab/bench/gen_workspace.py`）。採点は6項目を機械判定（`lab/bench/check.py`）。
- **モデル**: `gpt-6-luna`（Codex 契約経由、E011）。実行は `hermes -z`。各回は HERMES_HOME を複製して独立させ、月を変えた（`lab/bench/run_real.sh`）。
- **条件**:
  - C0: Skill なし（同梱 Skill 44個のみ）。
  - C1: Hermes 自作の汎用 Skill。1月分を実行させ「手順を再利用可能な Skill として保存せよ」と依頼して作らせた。
  - C1s: Hermes 自作のスクリプトつき Skill。「具体的なルールを書き込み、任意の月のレポートを作って検証するスクリプトを含めよ」と依頼して作らせた。
  - v2: ルール改定（保留中の注文も計上）後のデータで C0 と C1s。Skill は改定前のまま。
- **結果**（各3回の平均。詳細は `research/evidence/EV04-skill-reuse-results.md`）:

| 条件 | 合格 | API 呼び出し | 入力トークン | 所要秒 |
|---|---|---|---|---|
| C0 Skill なし | 3/3 | 11 | 187,862 | 44 |
| C1 汎用 Skill | 2/3 | 10 | 156,289 | 58 |
| C1s スクリプトつき Skill | 3/3 | 4 | 59,467 | 24 |
| v2 C0 Skill なし | 3/3 | 8 | 151,869 | 41 |
| v2 C1s 古い Skill | **0/3** | 5 | 74,173 | 25 |

  - C1 の Skill（`research/evidence/skills/monthly-sales-report-hermes-authored`）は社内ルールを含まず、「毎回ルールを読み直せ」「レポート固有の事実を Skill に入れるな」と書いていた。分類は `software-development`、説明は「Use when preparing monthly sales reports.」。
  - C1 の不合格1回は、数値は正しいが `CATEGORY:hardware=13378000 JPY` と単位を付けた形式違反。ルール文の `<integer JPY>` という書き方が曖昧で、こちらの仕様の落ち度でもある。
  - C1s の Skill はルールを箇条書きにし、5,115バイトのスクリプトを同梱した。エージェントは `skill_view` → スクリプト実行 → 確認、の3〜4手で終えた。
  - v2 の C1s は3回とも、ルール文書を一度も読まず、改定前の基準で計算したレポートを出し、成功として報告した。
  - Skill なしの条件でも、無関係な同梱 Skill `google-workspace` を読みに行く回が複数あった。
- **解釈**:
  - 効果は Skill の中身で決まる。手順の説明だけの Skill は効果が見えない。コードに固めた Skill は入力トークンを約3分の1、所要時間を約半分にした。発表の「説明文とコードの組み合わせ」という説明とは整合する。
  - 何も指定せずに書かせると、Hermes は汎用の手順書を書く。効く形の Skill は、こちらが形を指定して初めて得られた。自動の振り返りが効く形を書くかは未検証。
  - 速くなる理由と壊れる理由は同じ。「ルールを読まずに済む」ことが節約であり、ルール変更を見逃す原因でもある。「時間とともに信頼性が上がる」は、業務の前提が変わらない場合に限る。
  - 組織で共有した場合、古い Skill は「速く、自信を持って、間違える」。Skill の有効期限や前提の検査が要るが、Curator は利用頻度で古さを判定し、内容の正しさは見ない（EV01）。
- **限界・反証**:
  - 各条件3回で、条件内のばらつきが大きい（C0 の入力は 164k〜202k）。C0 と C1 の差は結論できない。C1s の差は範囲が重ならないので方向は確かだが、倍率は粗い。
  - 業務は1種類、モデルは1種類。Skill なしでも満点が取れる易しい業務なので、「品質が上がる」は測れていない。
  - Skill は依頼して書かせた。自動の振り返りが作る Skill ではない。
  - 入力の約85%はプロンプトキャッシュの読み出し。金額での差は、トークン数の差より小さくなる。
  - **無効にした実行**: 最初の比較（k2）は作業フォルダが研究フォルダの中にあり、Skill なし条件の3回中2回が親フォルダを検索して Skill の写しを読んでいた。作業フォルダを隔離してやり直した（k3 以降）。隔離しない限り、エージェントは作業フォルダの外を読む。
- **次の行動**: (1) ゲートウェイで自動の振り返りに Skill を書かせ、C1 と C1s のどちらに近いかを見る。(2) Skill なしでは失敗する難しい業務で品質への効果を測る。(3) 一覧に 500個の紛らわしい Skill がある条件。(4) 回数を増やす。
