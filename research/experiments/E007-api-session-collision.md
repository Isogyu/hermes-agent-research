# E007 API サーバーのセッション ID 衝突（2026-11-20）

- **目的**: E006 で、別々の環境の2回の実行が同じセッション ID `api-3399982e1e7d65f7` になった理由と影響を調べる。
- **背景・仮説**: `gateway/platforms/api_server.py:895-907` は、セッション ID を「システムプロンプト＋最初のユーザー発言」の SHA-256 先頭16桁で決める。仮説: 別々の利用者が同じ文で始めると、2人目のモデル入力に1人目の履歴が混ざる。
- **方法**: 同じゲートウェイに、`messages` が `Good morning` 1件だけのリクエストを2回送る。1回目の応答には架空の秘密 `ALPHA-42` を含める。2回目に偽 LLM へ届いたメッセージ列を確認。`lab/runs/g3-session-collision`。
- **結果**:
  - 2回とも `X-Hermes-Session-Id: api-e37826f1d1d9fc2c`。
  - 2回目のモデル入力は system と `Good morning` の2件だけ。1回目の応答は含まれていなかった。
- **解釈**: **仮説は否定**。会話履歴はリクエスト本文から組み立てられ、セッション ID の一致だけでは混ざらない。
- **残る懸念（未検証）**: コードのコメントによれば、この ID はセッションストアとセッション単位のサンドボックスの鍵になる。端末の作業ディレクトリや一時ファイル、振り返りのカウンタは共有されうる。Foundry 版は呼び出し元の OID から明示的にセッションキーを作る（EV02）ので、この既定の導出には頼っていない。
- **次の行動**: 優先度は低い。サンドボックス共有の確認は、端末ツールを使う2利用者の台本で行える。
